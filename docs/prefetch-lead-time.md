# 预取的 lead-time 预算：为什么「层的深浅」决定存储层级

> 状态：分析稿。回答一个问题：**能不能用前面层的计算把磁盘通信掩盖掉？**
> 答案：能，但**取决于模块在第几层**，而且 V4.1 的两个 Engram 模块差了 13 层 ⇒ 时效要求差一个数量级。
>
> 纪律：本文区分 **【实测】** / **【推算】** / **【假设】**。未被标为实测的数字不得引用为事实。

---

## 1. 时序模型

一个 decode step（batch 内含 B 条序列各出 1 token）：

```
t_n 被采样 ──► [调度器开销 O] ──► layer 0 ──► ... ──► layer L ──► ...
   rowid 在此刻全部已知                        ↑
                                        这里需要 Engram 数据
```

**核心事实**：Engram / PLE 的 rowid 是**输入 token 序列的纯函数**
（压缩词表 → 多 head 素数表哈希；官方文档原文：*"lookup index 只依赖输入 token 序列"*）。
所以 **`t_n` 一被采样，该 token 在任意层需要的全部 rowid 就已经确定** ——
不需要等模型走到第 L 层才算得出来。

这意味着预取起点可以放在 **token 生成时刻**（`design.md` §170 的判断），
而不是「快到达 Engram 层时」。这是本方案与「引擎内只重叠 Engram 层自身」的区别点。

### 1.1 定义

| 符号 | 含义 |
|---|---|
| `N` | Transformer 层数 |
| `L` | Engram 模块所在层号（zero-indexed） |
| `C(B)` | 一个 step 的 GPU 计算时间 |
| `O` | 一个 step 的**非计算**开销（调度、采样、Python、H2D） |
| `T = O + C(B)` | step 墙钟时间；batch=1 时 `T = 1/tok_s` |
| `F(B)` | 取回本模块在一个 step 内所需全部行的时间 |
| `τ(L)` | **lead time**：从 token 已知到 layer L 需要数据的窗口 |

### 1.2 lead time

层内计算近似均匀（`C/N` 每层）：

```
τ(L) = O + (L/N)·C
```

### 1.3 判据

```
完全掩盖  ⟺  F(B) ≤ τ(L)
留在关键路径上的代价  E = max(0, F(B) − τ(L))
相对代价              E / T
```

**设计要求**：模块放在第 L 层，则要么介质够快（F 够小），要么 O 够大：

```
L  ≥  N · (F − O) / C
```

## 2. V4.1 的实测几何

**【实测】** 来自 `docs/v41-engram-analysis.md` §1.2（config + 官方 shard header 闭合验证）：

| 项 | 值 |
|---|---|
| Engram 模块层号 | **layer 1 和 layer 14**（`engram_layer_ids = [1, 14]`） |
| 每 token 行数 | 2 层 × 3 阶 × 8 head = **48 行** |
| 每行记录 | 256 B FP8 + 8 B E8M0 scale = **264 B** |
| 每 token payload | **12,672 B** |
| Store-I 页流量 | 48 × 4 KiB = **196,608 B** |
| 层数 `N` | **【假设】按 61 层估算**（我们的记录里没有 V4.1 的 `num_hidden_layers`；此值只影响 τ 的绝对量，不影响 §4 的比值结论） |

**【实测】** 介质与路径（同机、同 `fadvise` 冷读口径，见 roadmap §32）：

| 量 | 值 |
|---|---|
| 4 KiB 裸随机读 QD1 | 77 µs |
| QD32 有效速率 | 2.74 µs/页 ⇒ **365 K IOPS**（约 1.5 GB/s 随机 4 KiB） |
| Store-I, t=32 | **220 µs/token**（44% of 500 µs 预算） |
| Store-P, t=32 | **7.69 µs/token**（1.5%） |

## 3. 代入：V4.1 在 100 tok/s 下

取 `T = 10 ms`（100 tok/s）。**【假设】** `O → 0`（大模型 + CUDA graph，调度开销可忽略）：

| | `τ(L)` | Store-I `F`=220 µs | Store-P `F`=7.69 µs |
|---|---|---|---|
| **layer 1** | `1/61 × 10 ms` = **164 µs** | 220 > 164 ⇒ 暴露 **56 µs**（0.56% of T） | 7.69 ≪ 164 ⇒ **完全掩盖** |
| **layer 14** | `14/61 × 10 ms` = **2.30 ms** | 220 ≪ 2300 ⇒ **完全掩盖** | **完全掩盖** |

**两条结论：**

1. **100 tok/s 下掩盖不是瓶颈，预算才是。** Store-I 即使在 layer 1 也只暴露 0.56%，
   Store-P 无论放哪层都是 0。
   ⇒ 「用前层计算掩盖通信」在 100 tok/s 下买到的是**余量**，不是可行性。
2. **13 层的间距 = 13×C/N = 2.13 ms ≈ Store-I 整个取数代价的 10 倍。**
   这就是 §4 的产品原语。

## 4. 「不同层对时效要求不同」的定量形式

### 4.1 比值

```
τ(14) / τ(1)  =  (O + 14C/N) / (O + C/N)
```

- `O → 0`（大模型、图捕获）⇒ 比值 → **14×**
- `O ≫ C/N`（小模型、eager、Python 调度器）⇒ 比值 → **1×**（此时 O 本身就够掩盖一切）

### 4.2 换算成介质要求

要被完全掩盖，介质需要提供的吞吐：

| 模块位置 | 允许的 `F` | 需要的随机读 IOPS（48 页/token） |
|---|---|---|
| layer 1 | ≤ 164 µs | ≥ **293 K** |
| layer 14 | ≤ 2.30 ms | ≥ **21 K** |

⇒ **layer 14 的模块可以放在比 layer 1 慢 14× 的介质上**，仍然完全掩盖。
若 layer 1 模块必须留在本地 NVMe，layer 14 就可以放到远端内存/RDMA/对象存储——
**这正是官方报告「宿主内存 + RDMA 预取 + per-module 分层」的数值依据**。

### 4.3 反向：批量与吞吐会把掩盖吃掉

`F(B)` 随 batch **近似线性**增长（每序列各要自己那 48 行，去重只在同页时有效），
而 `C(B)` 在权重受限的 decode 下**次线性**增长。于是：

```
F(B) / τ(B)  随 B 单调上升
```

**【推算】** 这个方向与直觉相反，但可测：**大 batch 是浅层 Engram 模块的敌人。**
batch↑ 让浅层模块从「被掩盖」滑向「暴露在关键路径上」。

同理，吞吐目标 `S` 上升时 `τ(L) = L/(N·S)` 线性缩小，而 `F` 不变：

| 目标 | `τ(1)` | Store-I 暴露 | 占 `T` |
|---|---|---|---|
| 100 tok/s | 164 µs | 56 µs | 0.6% |
| 200 tok/s | 82 µs | 138 µs | 2.8% |
| 400 tok/s | 41 µs | 179 µs | **7.2%** ← 超 5% 预算 |

⇒ **掩盖是 MTP/高吞吐的入场券**：100 tok/s 下可有可无，400 tok/s 下必需。

## 5. 跨 token 预测：被 n-gram 依赖堵死，除非推测

想用「整个 token 的计算」当 lead time，就必须在算 token n 的时候预取 token n+1。
但 2/3/4-gram 的 rowid 都以 `t_n` 结尾 ⇒ **`t_n` 出来之前一个都算不出**。

- **纯自回归：跨 token 预取不可能。** 只能吃 §1.2 的层内窗口。
- **有 MTP / 投机解码时可以**：候选 token 在验证前已知，可对 top-k 候选预取。
  代价是 k× payload。V4.1 的 payload 只有 12,672 B/token ⇒ k=4 也才 50 KB/token，很便宜。
  （vLLM 侧确实有 `Qwen3_5MTP` / `DeepseekV41` 的 MTP 注册，接口存在。）

**注意**：官方 V4.1 设计是「每个 pipeline stage 处理 micro-batch **之前**，
就对整个 local batch 发起预取」——**已经是本文 §1.2 的形态**（batch 粒度、token 生成时刻）。
所以真正的差距不在「要不要提前」，而在 **提前的窗口有多大** 和 **介质分层怎么配**。

## 6. 实测检验（4090 + vLLM 0.29.0 + Qwen3.5-0.8B）

**注意这里有两个模型，别混。** 下文实测跑在 **Qwen3.5-0.8B** 上，它**没有 PLE**
（`text_config` 一个 PLE 字段都没有）；`L` 与表的几何来自 **`qwen4_exp`**
（`Qwen3.8-Flash-Next`）。两者的关系是：**层的数量取自实测模型，PLE 的地址与 I/O
形状取自目标架构**，注入是合成的（随机投影）。

| 量 | 值 | 来源 |
|---|---|---|
| `N`（层数，实测） | 24 | Qwen3.5-0.8B `num_hidden_layers` |
| `L`（PLE 注入层） | 2 | `qwen4_exp` 的 `ple_layer_ids=[2]`，**不是** Qwen3.5-0.8B 的属性；脚本用 `--layer 2` 对齐 |
| 16 头 × 160 B | 2,560 B/token | `qwen4_exp` 的 `ple_embed_dim=2560` / 16 头 |

完整数据见 `probes/serve_ple_ab_session42.md`。

### 6.1 预测 P1 被**否证** —— 而且原因值得记下来

**预测**：小模型 eager serving 下 `O` 很大（≥1 ms），磁盘 reader 在 batch=1 几乎零代价。

**实测**：`O` 确实很大 —— 45 tok/s ⇒ `T ≈ 22 ms/token`，而 0.8B 在 4090 上的纯计算
只有微秒级，**22 ms 几乎全是引擎开销**。但磁盘臂仍然拿到 −2.4%（噪声地板 2.5%），
`engram-i` 的 913 µs/次取数**大部分仍落在关键路径上**。

**为什么错**：我把 `O` 放错了位置。`τ(L) = O + (L/N)·C` 里的 `O` 是
「token 已知 → 到达 layer L」之间的开销。但引擎的 per-step 开销（调度、Python、H2D）
发生在 **forward 之外**，而 rowid 是在 forward **之内**（`embed_tokens`）才第一次可得的。
所以层内 hook 能拿到的 lead time 只有：

```
τ_层内(L) = O_forward + (L/N)·C      O_forward ≈ 0，C/N 对 0.8B/4090 ≈ µs
```

**修正后的模型**：

```
τ(L) = [采样 → forward 开始] + [forward 内 layer 0..L 的计算]
     = O_inter-step  +  (L/N)·C
```

`O_inter-step` 只在**预取于采样点发起**时才计入。在层 hook 里取数 ⇒ `τ ≈ (L/N)·C ≈ 0`。

⇒ **这正是官方 V4.1 设计「stage 处理 micro-batch 之前对整批发起预取」的原因**：
不是风格选择，是唯一能拿到那 22 ms 的位置。

### 6.2 新的负面结果：Python 级预取让事情**更糟**

`prefetch-ub` 探针（后台线程取数、下一步消费）实测 **2525 µs vs 同步 913 µs，
端到端 −10.2% vs −2.4%**。

原因：取数路径 GIL 受限 —— rowid 生成 + `torch.frombuffer` + reshape 都在 Python 侧要 GIL，
后台线程与主线程是**争用**而非重叠。（`Store.fetch` 自身已 `allow_threads`，
膨胀来自 Python 组装。）

⇒ **能掩盖的前提是取数路径整体 GIL-free。** 因此：
rowid 生成 + 取数 + 张量构造应合并为**一次 PyO3 调用**，由一次 `allow_threads` 覆盖全程。

### 6.3 仍然成立的部分

- `τ(14)/τ(1)` 的 14× 比值：这是 `(L/N)·C` 的比值，与 `O` 放哪无关，**§4 的结论不受影响**。
- 「批量为敌」（§4.3）：仍未实测，见 §7。
