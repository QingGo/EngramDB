# Session 44 · 相位分解：把「存储代价」拆回它真正的归属

> 口径：真引擎（SGLang 0.5.19，`--cuda-graph-backend-decode=breakable`）、真表（128 分片、47.7 GiB）、
> 真 GPU（RTX 4090）。产物：`scripts/sc4_phase_microbench.py`、`scripts/sc4_reader_compare.py`、
> `probes/sc4_phase_microbench.json`、`probes/sc4_reader_compare.json`、
> `probes/sc4_sglang_native_reader.json`、`probes/sc4_delay_sweep_*.json`。

## 0. 这一轮的意义：§36.5 里那条前置条件兑现了

Session 43 用**臂间差值**归因成本，从 ±0.2 ms 的噪声里读出了「磁盘与 D2H 各占一半」，
并且写进了文档。那是错的。`§36.5 P1.5` 因此把「成本分解仪器」列为**前置**。

本轮把仪器建起来（离线相位微基准 + in-situ 相位计时 + 可控延迟扫描），
结论是：**上一轮那些数字几乎全部要改，而且改动方向指向同一个根因。**

## 1. 相位微基准（离线，无引擎）

### 1.1 D2H：是**排空流水线**，不是传数据

| 相位 | GPU 空闲 | GPU 忙（排队一个 4096³ fp32 matmul） |
|---|---|---|
| `d2h_1`（1 元素 `.tolist()`） | **11.5 µs** | **2428.1 µs** |
| `d2h_32` | 11.9 µs | 2563.8 µs |

**211× 放大。** 空闲时它只是一次 8 字节拷贝；有在途工作时它要等**全部**排队的 kernel。

> **⚠️ 我第一版基准把这个测反了。** 那版在计时**之前**调了 `torch.cuda.synchronize()`，
> 把「忙」这个条件本身排空了，于是「证明」D2H 不等 —— 它根本没有资格证明那件事。
> 这个 bug 已经写进脚本注释，因为它差点让整条 stage 2 的方向反过来。

**⇒ 消灭 D2H 不是省 11 µs，而是每步最多省下**整段在途流水线**的等待。这是 stage 2 的首项。**

### 1.2 其余相位都很便宜

| 相位 | 中位 |
|---|---|
| `rowid_1` / `rowid_8` / `rowid_32` / `rowid_128` | 51.5 / 50.2 / 54.2 / **68.6 µs** |
| `h2d_1024` pageable / pinned+non_blocking | 18.8 / **11.2 µs** |
| `add_1024` device | 10.8 µs |
| `empty_1024` device alloc | 7.3 µs |

**rowid 是 ~50 µs 的固定成本、边际几乎为零**（128 token 才 68.6 µs）。
Session 43 推出的「rowid ≈ 240 µs」同样是差值法的产物，同样是错的。
pinned H2D 省 7.6 µs —— 免费但微不足道。

### 1.3 Python 线程池在 ~3.3× 就饱和

| 配置 | 16 行冷随机读（中位） |
|---|---|
| `os.pread` 1 线程 | 1916.6 µs |
| 4 线程 | 627.4（3.06×） |
| 16 线程 | 604.0（3.17×） |
| 64 线程 | 576.6（**3.32×，饱和**） |
| 批到 128 token（`per_token`） | 464.1 |

**加线程到 64 只再拿 8%，跨 token 批量化几乎无用。** 577 µs 读 16 个 4 KiB = 27.7K IOPS，
而一块像样的 NVMe 是 500K+ IOPS —— **低了 18×，所以瓶颈不在盘。**

## 2. Reader 对比：同一批冷行，两种 reader

`scripts/sc4_reader_compare.py`（同样的 rowid、同样的冷态强制）：

| reader | 16 行中位 |
|---|---|
| Python `os.pread` pool1 | 1800.1 µs |
| Python pool16 | 554.6 |
| Python pool64 | 581.7 |
| **原生 `engramdb.Store.fetch`** | **276.7 µs** |
| 原生 `fetch_one` ×16 | 2116.2 |
| `StorePool`（**我的 harness bug**：每次调用新建 pool） | 2454.0 |

**原生比最好的 Python 池快 2.0×。**

⇒ **`t_read = 445–468 µs` 是 Python reader 的账，不是磁盘的账。**
而且 —— **我们自己的仓库就带着原生 reader，Session 43 的探针却手写了一个 Python reader**，
因此把 2× 的 reader 开销记到了存储头上，并在那之上做出了「差两层」的判决。

单线程 120 µs/行 → 16 路并发 6.3 µs/行，这正好是 16 路 × ~100 µs NVMe 延迟的算术结果
⇒ **并发确实有 ~19×，只是 Python 线程池拿不到。** 早先记录的「并发 18.1×」是对的
（它测的是原生/顺序路径），而我一度怀疑它错了 —— 这里更正回来。

## 3. 引擎内：换 reader 前后

| | Python reader（Session 43） | **native reader（本轮）** |
|---|---|---|
| `read_us_median` | 445–468 µs | **101–108 µs** |
| `read − break` | 1.30 ms | **0.261 ms** |
| `read − none` | 1.40 ms（**58.6%**） | **0.432 ms（17.9%）** |
| `readstatic − break` | +0.446 ms | **−0.127 ms** |

`readstatic − break` 变成负值（在噪声内）意味着：**没有 D2H 时，磁盘读被完整藏住了。**
四臂全部自证成立（`backend_replay` 495–576、`break_calls_in_replay` 与之一致、
三臂输出互异 sha1）。

## 4. 延迟扫描：把 `L*` 的分母实测出来

在断点里加可控忙等（`ENGRAMDB_SC4_DELAY_US`），扫 0→1600 µs，其余不变：

| delay | ms/tok | Δ vs `none`(=2.410) | break body | 被藏住的量 |
|---|---|---|---|---|
| 0 | 2.468 | +58 | 345 | **287** |
| 100 | 2.575 | +165 | 510 | **345** |
| 200 | 2.798 | +388 | 569 | 181 |
| 400 | 2.863 | +453 | 799 | 346 |
| 800 | 3.548 | +1138 | 1043 | **−95** |
| 1600 | 4.311 | +1901 | 1966 | 65 |

`break_us` 精确跟着 delay 走（345 → 1966，+1620 对 1600 ✓ 自证忙等准确）。
说明：body ≲ 800 µs 时能藏住 300 µs 上下；超过之后 **一点也不藏**，1:1 全暴露。

> ### **τ(1) ≈ 300–350 µs（±150 µs 量级的不确定度）**
>
> 而我一直用的 94.6 µs = `2.27 ms ÷ 24 层` 是**整步平均**，
> 把与层数无关的固定开销也摊进了层里 —— 那是我自己标注过「只是下界」的数。
> 真实窗口是「层 0 的 compute + 步间空隙」，**实测比平均值大 3 倍以上**。

## 5. 判决改写

`L* = ⌈t_read / 单层时间⌉` 的两个输入现在都实测了：

| `t_read` 来源 | 值 | `L*`（÷94.6） | 落在 τ(1)≈325 µs 内? |
|---|---|---|---|
| Python reader（Session 43 用的） | 445–468 µs | 5 | ❌ 否 |
| 原生 reader（引擎内） | **101–108 µs** | **2** | ✅ **是** |
| 原生 reader（独立脚本，强制狠冷） | 276.7 µs | 3 | ✅ 是 |

**⇒ 旧判决「Qwen PLE 差两层」是被 Python reader 的产物驱动的，不是被存储驱动的。**
换成原生 reader，`t_read = 101 µs ≪ τ(1) ≈ 325 µs`，
**PLE 放在 0-based 第 1 层是装得下的。**

**边界**：① 扫描点间散布 ±150 µs，所以「300–350」是量级而非精确值；
② τ(1) 是在 **Qwen3.5-0.8B 24 层**上测的，真实 PLE 模型是 48 层、MoE、单卡装不下
（185.5 GB），所以**这是替身模型上的窗口，不是目标模型上的**；
③ `t_read` 的两个数（101 引擎内 / 277 狠冷）差 2.7×，
差在冷的定义（独立脚本每次 rep 前 `fadvise` 掉 6.4 GB 页缓存）。

## 6. stage 2 的修正后顺序（按实测大小）

| # | 动作 | 依据 |
|---|---|---|
| **1** | **消灭 D2H** | 忙时 2428 µs / 闲时 11.5 µs —— 它等的是整段在途流水线，是最大项 |
| **2** | **用原生 `Store.fetch`，不要 Python 池** | 276.7 vs 554.6 µs；引擎内 101 vs 445 µs |
| 3 | pinned 暂存 + `non_blocking=True` | 18.8 → 11.2 µs（小，但免费） |
| 4 | rowid 移出关键路径 | ~50 µs 固定成本，收益最小 —— **不值得优先做** |

原 P1.5 把「持久线程池 + 跨 token 批量化」排第一。**实测推翻了它**：
线程池在 3.3× 饱和、批量化无用，真正的解法是换实现。

## 7. 教训

**差值法不能用来归因。** 本轮每一个被推翻的数（D2H 387、rowid 240、磁盘一半）
都来自「两个噪声总量相减」，而每一个被直接测量的数都推翻了一个差值结论。
`§36.5` 把成本分解仪器列为前置是对的；**在它存在之前，任何归因都只是猜测。**
